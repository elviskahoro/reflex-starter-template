# Migration prompt: RWX pipeline → RWX (cached prefix) + Dagger (portable core)

## Role and goal

You are migrating this repository's CI so that:

1. **All Dagger logic lives in `ci/`** (a plain Dagger SDK program: no Dagger module). The same functions run **locally** and **in CI**.
2. **RWX remains the orchestrator.** `.rwx/*.yml` caches every step it can with RWX's content-based cache (system packages, language runtimes, dependency installs, codegen, builds of unchanged inputs) and fans out in a DAG.
3. **The last cacheable step is the toolchain core** (the actual tests, Bazel/Gradle/Cargo/etc. build, lint, typecheck) and that step **invokes Dagger** from `ci/`.
4. **Local parity:** a developer with only Docker (or another Dagger-supported container runtime) and the `dagger` CLI can run `ci/run.sh all` (or the equivalent) and get the same result as CI, without RWX's cache.
5. Behavior is preserved. Same checks, same pass/fail semantics, same triggers, same secrets handling.

Do not start by writing code. Follow the phases in order and report at each gate.

## Phase 2: Design

### 2.1 Layout

```
ci/
  README.md           # how to run locally and in CI; cache behavior; env/secrets
  main.py             # plain Python program using the Dagger SDK; subcommands per check
  pyproject.toml      # ci/ deps only (dagger-io==X.Y.Z pinned) as ordinary Python packaging
  uv.lock             # lockfile (or the repo's existing convention)
  run.sh              # thin wrapper: `dagger run python ci/main.py "$@"`
.rwx/
  ci.yml              # Layer A + B tasks; final task(s) call Dagger
```

**No Dagger module and no Dagger config files (`dagger.toml`, `dagger.json`).** `pyproject.toml` for Python deps is allowed. The language is **Python**, regardless of the repo's primary language: use the Dagger Python SDK (`dagger-io`), with `ci/` as a Python project (own `pyproject.toml` + lockfile, or the repo's existing root one, pinned SDK and Python versions; prefer `uv` (match the repo's existing convention if it has one). `pyproject.toml` is fine for Python deps; the ban is only on Dagger's own config). Write one small, typed program (`ci/main.py`) whose CLI takes a subcommand per logical check (`test`, `lint`, `typecheck`, `build`, `bazel-test`, …) plus `all`. Entry point everywhere (local and RWX): `dagger run python ci/main.py <subcommand>`. **Version pairing:** pin the Dagger CLI and `dagger-io` in lockstep on the same release line (this org's working pipelines use the 0.21.x line, e.g. `dagger-io==0.21.8` with CLI `0.21.8`; CLI/SDK/engine skew surfaces as confusing runtime errors). On that line the entry point is `dagger run`. Dagger 1.0 (the current default install) renamed it to `dagger api with-session` (https://docs.dagger.io/migrate-to-v1), so if you re-pin to 1.x, update the entry point at every site in `ci/run.sh`, `.rwx/*.yml` and the docs. Wrap it in `ci/run.sh` or a Makefile/package-script target so the command is short.

### 2.2 Principles for the Dagger program

- **Hermetic and deterministic.** Pin base image digests/tags, toolchain versions, and package-manager lockfiles. No `latest`.
- **Layer for cache.** Order operations least-to-most-changing: toolchain → dependency manifests/lockfiles only → install → full source → run. Mount only the files needed per step (use directory filters/ignore patterns; never mount `.git`, `node_modules`, build outputs, or `.context/` unless required).
- **Cache volumes** for package managers and build tools (npm/pnpm/yarn store, pip/uv, Go mod/build, Cargo registry/target, Gradle, Bazel disk cache/output base, etc.). Use a stable cache-volume key per tool. Never put secrets or non-reproducible state in cache volumes.
- **Secrets via Dagger `Secret` arguments**, never baked into layers, env literals, or logs. Read from env/file/command providers at the CLI boundary.
- **No hidden host dependencies.** The program takes the repo path (default: repo root) and loads it as a Dagger `Directory` via the SDK host API. It must not rely on the caller's installed language toolchains.
- **Services** (Postgres, Redis, browsers, emulators) as Dagger service containers with explicit health/wait semantics.
- **Exit codes and output matter.** A failing test must fail the Dagger function and therefore the check. Export useful artifacts (JUnit XML, coverage, build outputs, screenshots) via `Directory`/`File` return values or `export`, to a path CI can collect.
- **Layer A overlap rule:** do not duplicate in Dagger what RWX already prepared if that forces a double install. Follow the layering in 2.3: RWX tasks prepare toolchains and caches; the Dagger program consumes only what it cannot get from RWX.
- **Parity with local:** the same function with the same arguments must work in both places. Differences (e.g. extra secrets, remote cache endpoints) come only from arguments/env, not from separate code paths.

### 2.3 Caching: RWX is the only cache (decided; do not add Dagger Cloud)

Use **RWX's content-based cache and `tool-cache` for everything**, including Dagger's state. No Dagger Cloud or external cache service. The mechanism below is proven in production in a sibling repo (see Appendix A); reuse it, and verify each piece against `rwx docs` before relying on it.

1. **Layer A in RWX tasks** (uv, Python, Dagger CLI, SDK venv, language/build toolchain, codegen): tight `filter`s, and **no `use: code`** unless the task reads repo files. A task that `use`s the checkout gets a new cache key every commit; keep install/warm tasks off it so they stay content-cache hits across commits.
2. **Dagger CLI**: install the checksum-pinned release tarball (verify sha256 against the release `checksums.txt`) in its own task with no `use:`. **Dagger SDK**: `uv venv` + `uv pip install "dagger-io==X.Y.Z"` in its own task, no repo reads.
3. **Engine image warm task**: `docker: preserve-data`, `use: [dagger-cli-install]` only; it `docker pull`s `registry.dagger.io/engine:<version>` (with retries) so test tasks don't pay the cold pull. Without `docker:` RWX starts no Docker daemon.
4. **Final Dagger task(s)**: `docker: true`, `use:` the checkout + toolchain + SDK + engine-warm tasks, and `timeout:` raised (RWX defaults to 10m; cold runs get killed otherwise).
5. **Build-tool cache across runs**: have the Dagger program **export its cache** (e.g. the Bazel disk/repo cache, package-manager stores) to a host directory (tar or directory export, path passed via an env var like `CI_CACHE_DIR`, exported by an earlier task through `$RWX_ENV`) and persist it with RWX **`tool-cache: <name>`** on the final task(s). Import it back into the Dagger container at the start of the run. Gate with an env flag (`CI_CACHE_WRITE`) so only the intended runs export (exporting multi-GB caches on every run wastes minutes).
6. **Write-access policy**: scope tool-cache writes with an RWX **vault** (`tool-cache: { vault: <repo>-main }` at the top level) so only main writes; PR runs restore main's cache but never write it. Note the tool-cache TTL (observed 48h, not extended by incremental writes) and add a scheduled **cache-rebuild** trigger (cron/dispatch targeting just the final task with an empty diff base so it runs the full suite) to refresh it before it lapses.
7. **Export real paths** from setup tasks with `echo "$X" >> $RWX_ENV/NAME` (e.g. `CI_CACHE_DIR`, venv `bin` on `PATH`) rather than hardcoding `/root` or `$HOME` in downstream tasks.

Report: size of the persisted cache, restore time vs. cold-build time saved, and that a lockfile/toolchain bump invalidates the right layer. If a piece isn't feasible on the runner, fall back to Layer A caching only and say why, with measurements. Never fall back to a non-RWX cache.

The **local command must remain the same** and must work with no CI-specific services; locally Dagger just uses its normal engine cache and the cache-export env vars are unset.

Confirm early that the runner can run the Dagger engine (`docker: true`). Per this org's conventions Dagger cannot run in Conductor cloud sandboxes: validate it in an RWX task (and locally on a machine with Docker).

### 2.4 Cache-key discipline in RWX

For each RWX task, set inputs so the content-based cache keys are as tight as possible: use `filter` to restrict to the files the task truly reads (lockfiles, manifests, config, specific source dirs), put slow-but-stable tasks early with narrow filters, and push the high-churn source into the **last** task only. The rule: **a change to application source should invalidate only the final Dagger task, nothing before it.** If a doc-only change invalidates the install task, fix the filters.

## Appendix A: Reference implementation (same architecture, already working)

A sibling repo (a Bazel + pytest monorepo) already does this; mirror its shape, not its repo-specific details. Its `.rwx/tests-bazel.yml` and Python Dagger program (`scripts/ci/bazel_dagger.py`) work like this (the new repo should put its program in `ci/` instead):

**DAG**
```
captain ─────────────────────────────┐ (test-result reporting CLI; optional)
github-cli ─► changes (github/compare w/ globs) ─► [skip-gate]
github-cli ─► head-moved (cron only)             ─► [skip-gate]
git-credentials ─► code (git/clone, full depth) ─► git-history (detached clone, remote rewritten)
uv-install [if skip-gate] ─► dagger-sdk-install (uv venv + dagger-io==X.Y.Z)
uv-install + code(filter: toolchain script only) ─► toolchain (pinned tools, cache hit until pins change)
dagger-cli-install (no use:, checksum-pinned tarball)
  ─► dagger-engine-warm [if skip-gate, docker: preserve-data]
final: use [code, git-history, toolchain, dagger-sdk-install, dagger-engine-warm, captain]
       docker: true, tool-cache: <name>, timeout: 30m+  ─► runs `dagger run python <program>` (via `captain run` for reporting)
```

**Patterns worth copying**
- **One Python program, many steps.** The same program is selected by an env var (e.g. `BAZEL_DAGGER_STEP=plan-full | build-full | test-shard`) or subcommand, and by mode env flags (`RUN_IMPACTED`, `RUN_FULL`, `DIFF_BASE_SHA`). RWX tasks are thin: set env, call `dagger run python …`. Full-suite work is split into parallel RWX tasks (`plan`, `build-full`, `bazel-full`) so the fast gate and build-everything don't sit on the test path.
- **Skip gate.** A shared YAML alias (`&skip-gate`) on the root heavy task(s); RWX skips all dependents. The `changes` task (github/compare + broad `patterns:` globs: sources, build files, lockfiles, CI scripts, the RWX yml itself; err wide, a false positive costs one run) runs on every trigger on purpose, because a gate that reads a *skipped* task's value is itself skipped. Non-PR triggers pass `base-sha == commit-sha` so the diff is empty and other clauses decide.
- **Impacted vs. full mode** via `init.mode` (push/PR → impacted; cron/dispatch/cli → full). On a new branch `before-sha` is all-zero: fall back to full when `git cat-file -e` fails on the base.
- **Triggers** (`on.github.push/pull_request`, `cron`, `dispatch`, `cli`, and a `cache-rebuild` target) all feed the same `init:` params. Cron triggers expose `event.git.*` and `event.cron.*` (see rwx.com/docs/cron-schedules); the sibling repo uses only `event.git.*` and literals, and a test enforces it. Use string `"true"/"false"` for init flags that flow into env.
- **Security.** Fork PRs never get secrets: gate secret-carrying tasks/triggers on same-repo + trusted author; skip trunk-merge queue branches if not a required status. Pin installer scripts and binaries by sha256.
- **Self-contained git history** for diff-based logic: full-depth clone, then `git clone --no-local` into a second detached copy with `origin` rewritten to the real URL; export its path via `$RWX_ENV`. For PRs, fetch the base branch into that copy with a `GIT_ASKPASS` helper so the token stays out of argv/URLs.
- **Reporting.** `captain run <suite>` wraps the Dagger call to upload test results (e.g. to Trunk) with results in a `CAPTAIN_RESULTS_DIR`; make upload failures non-fatal off-PR so a failed upload can't discard the tool-cache layer.
- **Root-owned cache dirs.** Containers may leave root-owned files in the exported cache; `chown -R "$(id -u):$(id -g)"` the cache dir before reuse.

**Pitfalls it hit (put these in your checklist)**
- Warm/install tasks that `use: code` never cache-hit; they re-ran every commit.
- No `docker:` key → "Cannot connect to the Docker daemon".
- Default 10m timeout killed an otherwise-passing cold run.
- Writing the multi-GB cache on every main push uploaded a huge layer for nothing; restrict writes (flag + vault) to cache-rebuild/nightly runs.
- A gate that reads a skipped task's value is itself skipped and silently skips the chain.
- Sharing the repo's root `pyproject.toml`/`uv.lock` with the CI code is fine (add `dagger-io` pinned as a dependency, e.g. a `ci` dependency group). Scripts that need no project deps can use `uv run --no-project`.
